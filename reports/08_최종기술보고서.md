# 산출물 8. 최종 기술 보고서 — 콩잎 질병 분류 Vision AI 서비스

> ResNet-18을 콩잎 3클래스로 Fine-tuning하고, FastAPI 동기 API · Redis 캐시 · Celery 비동기 작업 · PostgreSQL 작업 기록을 Docker Compose로 묶어 서비스했다.
> 제공 코드 그대로의 기준선(Head-only) Validation **0.767**에서 Full Fine-tuning + 증강으로 **0.993**까지 올려 모델을 선택했고, 선택된 모델의 **최종 Test 정확도는 0.953**이다.
> 가장 위험한 오류인 **"병든 잎을 정상으로 놓침"은 Validation 11장 → 1장, 최종 Test 0장**이다. 모든 수치는 실제 실행 결과다.

## 3. 모델 결과

![모델 선택과 최종 평가](figures/val_vs_test.png)

| ID | 학습 방식 | 바꾼 것 | 학습 파라미터 | 학습률 | Train 증강 | Validation | Val 병을 놓침 |
|---|---|---|---|---:|---|---:|---:|
| E1 | Head-only (필수 기준선) | 제공 명령 그대로 (`--freeze-backbone`) | 분류 헤드 1,539개 | 0.0002 (기본값) | 없음 (제공 코드에 증강 기능 없음) | 0.7669 | 11 |
| E2 | Full Fine-tuning | `--freeze-backbone` 제거 + `--lr 0.00005` (가이드 6-1 B) | **전체** (약 1,118만 개) | 0.00005 | 없음 (Full 효과만 보려고 뺌) | 0.9699 | 2 |
| **E3** ⭐ | Full + 증강 | E2에 **Train 증강만** 추가 (`training/finetune_aug.py`) | 전체 | 0.00005 | 좌우 반전 50% · 회전 ±20° · 밝기·대비 ±0.2 | **0.9925** | **1** |

공통 조건: epochs 3 · batch 8 · 같은 Train 1,034장 / Validation 133장 · 제공 `finetune.py` 미수정.

- **Full Fine-tuning에서 한 일:** 제공 코드는 `--freeze-backbone`을 주면 이름이 `classifier.`로 시작하는 층만 `requires_grad=True`로 두고 나머지(Backbone)는 고정한다. E2는 이 옵션을 빼서 **Backbone의 합성곱 층까지 모두 콩잎 데이터로 다시 학습**했다. 이미 ImageNet으로 잘 학습된 가중치를 크게 흔들면 사전학습 특징이 망가지므로 학습률을 기본값의 ¼(0.00005)로 낮췄다. 동결 해제와 학습률은 가이드 B 설정대로 함께 바꿨으므로 두 효과를 따로 분리하지는 않았다.
- **증강(E3)에서 한 일:** Train 사진을 읽을 때마다 무작위 변형을 적용해 매 epoch 조금씩 다른 사진을 보게 했다. 촬영 방향(반전·회전)과 조명(밝기·대비) 차이를 흉내 내되, 병을 구분하는 색 단서를 지키려고 **색조·채도는 바꾸지 않았다.** Validation에는 적용하지 않았다. 상세는 6장 ①.

| **최종 평가 (E3, Test 1회)** | 정확도 **0.9531** · Macro-F1 0.9534 · 병을 놓침 **0** · 정상 오경보 0 · 남은 오답 6장 모두 질병 간 혼동 |
|---|---|

- **Backbone까지 학습한 효과가 결정적이었다.** E1의 Val 오답 31장 중 16장이 두 질병 간 혼동, 11장이 질병→정상 누락이었다. ImageNet 특징을 고정한 채로는 병반의 미세한 차이를 구분하지 못했다.
- **증강 효과는 확정하지 않는다.** E3는 Val에서 E2보다 3장 더 맞혀 사전 규칙을 충족했지만, 시드 1개·1회 실행이라 향상 폭을 일반화하지 않는다.
- **Test가 Val보다 낮은 것은 예상된 결과다.** Val은 best epoch와 모델 선택에 모두 쓰여 낙관적이다 (0.9925 → 0.9531).

## 4. 시스템 구조

![시스템 구성도](figures/architecture.png)

- 동기: 브라우저 → web → Redis 캐시(HIT면 즉시) → ResNet18 → 200
- 비동기: 브라우저 → web → `media/jobs` 저장 → PostgreSQL `queued` → Redis 브로커 → worker → 캐시 확인·추론 → `done` → 브라우저가 1초마다 조회
- web과 worker가 **같은 캐시를 공유**하고, 모델은 **각 프로세스에 따로 로드**된다.
- 평가 가이드 그림(FastAPI·Celery는 WSL)과 달리 **02 교재 22번 방식으로 4개 서비스를 모두 컨테이너로 실행**했고, 증빙은 모두 이 구조에서 수집했다. 상세: [산출물 2](02_시스템_아키텍처.md)

### ① 이미지 증강 (구현·실측)

| 증강 | 설정 | 이유 |
|---|---|---|
| 좌우 반전 · 회전 ±20° · 밝기·대비 ±0.2 | Train에만 | 촬영 방향·조명 차이 |
| 색조(hue)·채도 | **변경 안 함** | 녹병(적갈색)과 반점병(황갈색)은 색이 핵심 단서 → 라벨과 맞지 않는 이미지 생성 위험 |

- 학습 곡선: E2는 Loss가 0.09까지 내려갔지만 Val은 epoch 1이 최고 → 학습 이미지에 맞춰지는 경향. E3는 Loss가 0.14로 덜 내려갔지만 Val이 계속 상승 → 규제 효과로 해석 (`figures/training_curves.png`).
- 결론: **Val에서 +3장으로 선택 규칙을 충족**했지만, 1회 실행이라 향상 폭은 확정하지 않는다.

### ③ Grad-CAM (분석) — 모델은 어디를 보고 틀렸나

![Grad-CAM 오답 분석](figures/gradcam/gradcam_summary.png)

- 열 구성: 원본 · E3 예측 근거 · E3의 정답 클래스 근거 · 같은 사진의 E1 예측 근거
- **E3의 근거는 오답 7장 대부분에서 잎 영역(일부 줄기·가장자리 포함)에 있었다.** 문제는 배경이 아니라 병반 특징의 구분이다.
- **같은 사진에서 E1는 7장 중 3장(`bean_rust_test.15`, `.28`, `.3`)에서 흙·배경 쪽에 근거가 있었다.** Full Fine-tuning이 "보는 곳"을 잎 쪽으로 옮긴 정황이다.
- 한계: **오답 사진만 본 관찰**이라 일반화할 수 없다. Grad-CAM은 7×7 특징 지도에서 시작해 작은 녹병 돌기 하나하나를 짚지 못한다.
- E1가 맞히고 E3가 틀린 사진도 있다 (`bean_rust_val.8`: E1 bean_rust 0.56 / E3 healthy 0.95).

### ② OpenCV HSV (분석) — 색으로 병반을 셀 수 있나

![HSV 병반 후보 분석](figures/hsv/hsv_summary.png)

처리: `cvtColor(BGR→HSV)` → 녹색 `inRange` → `Opening` → 잎 안쪽 구멍 채우기(테두리와 이어진 흙·배경 제외) → 잎 안의 갈색·황갈색 픽셀 = 병반 후보 → 면적비

| 클래스 (Validation) | n | 병반 면적비 p25 | **중앙값** | p75 | 병반 색조 중앙값 (H) |
|---|---:|---:|---:|---:|---:|
| angular_leaf_spot (반점병) | 44 | 0.0084 | **0.0154** | 0.0296 | 20 |
| bean_rust (녹병) | 45 | 0.0032 | **0.0067** | 0.0186 | 19 |
| healthy (정상) | 44 | 0.0020 | **0.0068** | 0.0148 | 20 |

- 반점병은 병반이 크고 뚜렷해 면적비가 높았지만, **녹병과 정상은 중앙값이 거의 같았다.** 녹병의 작은 돌기는 256×256 축소에서 잘 잡히지 않고, 정상 잎에서도 손·흙·잎 구멍이 병반 후보로 잡혔다.
- 색조(H) 중앙값도 세 클래스가 19~20으로 같아 **색조로 두 질병을 나눌 수 없었다.**
- E3가 healthy 0.95로 틀린 `bean_rust_val.8`은 병반 면적비 0.0014로, **모델과 색 규칙 모두 병반을 보지 못한 사례**다.
- 방법상 한계: HSV 색 범위는 소수 샘플 화면을 눈으로 보며 정했다. 그래서 HSV 결과는 참고용이며 서비스 판단에 쓰지 않는다.

### ④ 규칙 기반 보조 판단 (오프라인 시뮬레이션)

라벨을 바꾸지 않고 **"확인 필요"만 표시**하는 규칙을 Validation에서 정하고 효과를 확인했다.

| 규칙 | 조건 | 기준값 출처 |
|---|---|---|
| R1 정상 의심 | 예측이 healthy인데 병반 면적비 > **0.0249** | Val에서 healthy를 맞힌 사진의 95백분위 |
| R2 저신뢰 | 1·2위 점수 차 < **0.4** | E1 Validation margin 분석 (0.4 이상 구간 정확도 97.6%) |

| 규칙 (Validation 133장) | 보류 | 보류율 | 잡은 오답 | 보류 안 한 사진의 정확도 |
|---|---:|---:|---:|---:|
| R1 정상 의심 | 3 | 2.3% | 0 / 1 | 0.9923 |
| R2 저신뢰 | 4 | 3.0% | 0 / 1 | 0.9922 |
| R1 ∪ R2 | 7 | 5.3% | 0 / 1 | 0.9921 |

- **R1(색 규칙)은 기각한다.** 유일한 오답(`bean_rust_val.8`)은 병반 면적비가 0.0014로 낮아 잡히지 않았고, 정상 잎 3장만 보류했다.
- **R2(점수 차 규칙)는 적용을 보류한다.** E3의 Validation에는 점수 차가 작은 오답이 없어(유일한 오답의 점수 차 0.90) 효과를 확인할 근거가 없다. 기준 0.4도 E1 분석에서 가져온 값이다.
- **확신을 갖고 틀린 사례는 어떤 규칙으로도 잡지 못한다.** 점수와 독립적인 새 근거가 필요하다.
- R2의 효과는 **새 데이터로 다시 검증**해야 한다.
- 원본: `reports/data/hsv_rule_summary.json`, `hsv_features_val.csv`

### 제안만 한 기술 (미구현 · 효과 미검증)

| 기술 | 아이디어 | 이번 분석에서 얻은 근거 | 확인 방법 |
|---|---|---|---|
| 고해상도 입력 / 타일 분할 | 224×224 축소로 사라지는 작은 녹병 돌기 보존 | HSV·Grad-CAM 모두 작은 돌기를 놓침 | 같은 Val에서 입력 크기만 바꿔 비교 |
| 잎 ROI · GrabCut | 손·흙·배경을 지운 잎만 입력 | E1는 배경을 봤지만 E3는 이미 잎을 봄 → 우선순위 낮음 | 마스크 입력 모델을 같은 분할로 학습 |
| 학습 범위 밖 입력 거르기 | "콩잎이 아님" 판정 (잎 면적비 하한 또는 별도 이진 분류기) | 고양이 사진 → bean_rust 0.525 | 콩잎/비콩잎 검증 세트 구축 |
| CNN + ML 융합 | CNN 점수 + HSV·Contour 특징 → RandomForest 보조 분류 | 현재 HSV 특징은 녹병·정상 구분력이 낮음 | Train 내부 교차검증으로 특징 생성 |
| ORB / SIFT | 반점 질감의 국소 특징 | 색보다 질감 차이가 클 가능성 | Val에서 특징점 매칭 품질 비교 |
| 반복 실험 | 시드 3~5개로 E2·E3 재학습 | 증강 효과가 1회 실행으로는 불확실 | 평균 ± 표준편차 비교 |

## 10. 한계

1. **데이터:** 단일 출처(Makerere beans), Test 128장(1장 = 0.78%p). 다른 지역·카메라·조명의 현장 사진에서는 미검증.
2. **실험:** 각 실험 시드 1개 1회 실행. 증강 효과는 불확실.
3. **모델 판단:** score는 보정된 확률이 아니며, 확신 오답(0.95)이 존재한다. "콩잎이 아님"을 판단하지 못한다.
4. **시스템:** 동시 요청 부하는 측정하지 않았다. worker는 solo·1개라 작업이 몰리면 순서대로 처리된다.
5. **실행 방식:** 평가 가이드의 WSL 실행 방식으로는 02 통합을 검증하지 않았다.
